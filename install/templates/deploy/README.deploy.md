## Ship workflow (copy → install → serve)

On a **clean target** (desktop PC or server):

1. **Copy** this entire `deploy/{{harness_name}}/` folder to the host (scp, rsync, CI artifact, USB, …).
2. **Install** runtime deps with the bundled target install (once per host / after each redeploy):

   | OS | Command (from inside this folder) |
   |---|---|
   | **Windows (PowerShell)** | `.\target-install.ps1` |
   | **macOS / Linux** | `./target-install.sh` |
   | **Any OS** | `python target_install.py` |

   Or from a checkout that already has `install/`:  
   `python install/target_install.py --deploy-dir /path/to/deploy/{{harness_name}}`

3. **Create `.env`** on the target from `.env.example` if present — **never** ship secrets inside this bundle. Put provider API keys in `.env` only.
4. **Serve** from the **project root** that contains `deploy/{{harness_name}}/` (not from inside the bundle folder):

   ```bash
   zaumzeug doctor {{harness_name}} --deploy
   zaumzeug serve {{harness_name}} --deploy
   # containers / systemd (no --deploy flag):
   HARNESS_ROOT=deploy zaumzeug serve {{harness_name}}
   ```

**Redeploy:** ship a new `deploy/{{harness_name}}/` → re-run `target_install` → serve. Do **not** `pip upgrade` ad hoc on the server.

**Linux-first production:** The supported ops target in v1 is Linux (VM, bare metal, Docker/Kubernetes). Phase 2+ CI requires `zaumzeug deploy` → `zaumzeug serve --deploy` smoke on Linux (`ubuntu-latest`).

**Optional container path:** A generated Dockerfile inside the deploy bundle is planned for Phase 4 (E8-S05). Until then, run with `HARNESS_ROOT=deploy` inside your own Python 3.11+ image after `pip install zaumzeug`.

## Target install (once per host)

Python **3.11+** must already be on PATH. From this directory:

| OS | Command |
|---|---|
| **Windows (PowerShell)** | `.\target-install.ps1` |
| **macOS / Linux** | `./target-install.sh` |
| **Any OS** | `python target_install.py` |

`target_install` creates an optional `.venv`, runs `pip install zaumzeug` (**runtime only** — no `[dev]`, `[eval]`, DSPy, GEPA, or DeepEval), verifies `manifest.json` + `harness.yaml`, and seeds `.env` from `.env.example` when missing (never overwrites). Shell wrappers (`target-install.sh` / `.ps1`) forward flags and exit codes. Optional `--verify` runs `zaumzeug doctor <name> --deploy` then `zaumzeug serve <name> --deploy --dry-run` (non-zero exit on failure).

## Serve

From the **project root** that contains `deploy/{{harness_name}}/` (not from inside the bundle folder):

```bash
zaumzeug serve {{harness_name}} --deploy
# equivalent env override (containers / systemd):
HARNESS_ROOT=deploy zaumzeug serve {{harness_name}}
# MCP (Cursor / Claude Desktop) — same production root, same MCP surface as dev:
zaumzeug mcp {{harness_name}} --deploy
# ACP (Zed / JetBrains):
zaumzeug acp {{harness_name}} --deploy
```

`--deploy` or `HARNESS_ROOT=deploy` loads **only** this production tree — no `usr-harnesses/` required. The OpenAI-compatible API matches dev serve:

| Endpoint | Purpose |
|---|---|
| `POST /v1/chat/completions` | Chat — `"model": "{{harness_name}}"` |
| `GET /v1/models` | Lists the served harness |
| `POST /{{harness_name}}/run` | Direct Hayhooks run API for the entry agent |
| `POST /<pipeline-id>/run` | Exposed Haystack YAML from `serve.expose` (copied into this bundle) |
| `GET /docs` | FastAPI Swagger UI for manual REST probes |
| `GET /chat` | Optional Chainlit GUI — only if `serve.hayhooks.chainlit: true` and `pip install "hayhooks[chainlit]"` on the target |

Web clients (Open WebUI, SPA + Nginx, Next.js) set OpenAI `baseURL` to this server's `/v1` (for example `http://127.0.0.1:1416/v1`, or `http://hayhooks:1416/v1` on a Docker network) — **not** `https://api.openai.com/v1`. Layout recipes live in the project's `user-docs/guides/web-deployment.md`.

## Production auth (proxy-only)

**Hayhooks has no built-in auth in v1.** There is no `serve.auth`. Do not publish this process on the public internet.

Put **Traefik** (reference) in front: TLS termination + Headers middleware (HSTS) + ForwardAuth or bearer check at the edge. The harness stays unauthenticated on `127.0.0.1` (or a Docker internal network). Nginx/Caddy work the same way.

Optional Traefik static/dynamic YAML ships in this bundle under `traefik/` — **secret-free**. Set `HARNESS_API_KEY` / OIDC client secrets / ACME email on the **Traefik host** only (systemd `EnvironmentFile`, Docker secret). Never put credentials in `harness.yaml`, `traefik/*.yml`, or git.

Public path map (Traefik → localhost):

| Path | Backend |
|---|---|
| `/v1/chat/completions` (REST) | `127.0.0.1:1416` |
| `/chat` (Chainlit, if enabled) | `127.0.0.1:1416` |
| `/mcp` (MCP) | `127.0.0.1:1417` |

Full guide: the project's `user-docs/guides/production-auth.md`.

Validate without binding a port:

```bash
zaumzeug doctor {{harness_name}} --deploy
zaumzeug serve {{harness_name}} --deploy --dry-run
```

## MCP (Cursor / Claude Desktop)

Production MCP uses the **same** `deploy/{{harness_name}}/` tree as serve — no `usr-harnesses/` required. The Streamable HTTP surface matches `zaumzeug mcp` in development (`POST /mcp`, `GET /status` on `serve.hayhooks.mcp_port`, default **1417**).

From the **project root** that contains `deploy/{{harness_name}}/`:

```bash
zaumzeug mcp {{harness_name}} --deploy
# equivalent env override (containers / systemd):
HARNESS_ROOT=deploy zaumzeug mcp {{harness_name}}
```

Cursor / Claude Desktop URL (localhost bind, same Phase 1 rule as serve):

```text
http://127.0.0.1:1417/mcp
```

Override the port with `--port N` or `serve.hayhooks.mcp_port` in the shipped `harness.yaml`. Reverse-proxy to `{mcp_port}/mcp` for a remote host.
