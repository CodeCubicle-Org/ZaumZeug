# Deploy and ship

| | |
|---|---|
| **Audience** | Ops / platform · Harness developers |
| **Last updated** | 2026-07-29 |

Ship a production harness to a clean server **without** DSPy, GEPA, or DeepEval on the target. Compile and eval stay on the developer machine (or CI); the target only runs Haystack via `zaumzeug`.

For the copy that ships **inside** each bundle, see that folder's `README.deploy.md` (generated by `zaumzeug deploy`).

---

## End-to-end path

```text
dev/CI:  zaumzeug compile <name>  →  zaumzeug deploy <name>
              ↓
         deploy/<name>/   (self-contained bundle)
              ↓
target:  copy folder  →  target_install  →  create .env  →  zaumzeug serve <name> --deploy
```

| Step | Where | What |
|---|---|---|
| 1. Package | Dev / CI | `zaumzeug deploy <name>` writes `deploy/<name>/` (stripped yaml, pinned artifacts, `manifest.json`, `README.deploy.md`, target install scripts) |
| 2. Copy | Ops | Copy **only** `deploy/<name>/` to the target (no `usr-harnesses/` required) |
| 3. Install | Target | Run bundled `target_install` → `pip install zaumzeug` (**runtime only**) |
| 4. Secrets | Target | Create `.env` from `.env.example` if needed — **never** ship `.env` in the bundle |
| 5. Serve | Target | `zaumzeug serve <name> --deploy` (or `HARNESS_ROOT=deploy`) |

---

## Prerequisites (target host)

| Requirement | Required? | Notes |
|---|---|---|
| **Python 3.11+** | Yes | Must pre-exist on PATH — install scripts do **not** install Python |
| **`pip install zaumzeug`** | Yes | Runtime install — Haystack / Hayhooks come via the SDK |
| **DSPy / GEPA** | No | Compile on dev/CI only |
| **DeepEval / `[eval]`** | No | Optional on **dev**; not installed on production by default |
| **`usr-harnesses/`** | No | Production loads `deploy/<name>/` only |
| **`.env`** | For live models | Create on the target; never packaged into `deploy/` |

Approximate disk: **~500 MB–1.5 GB** for a runtime venv (no `[dev]` / `[eval]`).

## Target install — Win / macOS / Linux

After the bundle is on the host, run install **from inside** `deploy/<name>/` (or pass `--deploy-dir`):

| OS | Command |
|---|---|
| **Windows (PowerShell)** | `.\target-install.ps1` |
| **macOS / Linux** | `./target-install.sh` |
| **Any OS** | `python target_install.py` |
| **From repo `install/`** | `python install/target_install.py --deploy-dir deploy/<name>` |

What install does (Architecture §10.7; core script **Done** E5-S09a):

1. Preflight — require Python 3.11+, `harness.yaml`, and `manifest.json`
2. Optional `.venv` beside the bundle (unless `--skip-venv`)
3. `pip install zaumzeug` — **not** `zaumzeug[dev]` or `zaumzeug[eval]`
4. Seed `.env` from `.env.example` when missing (**never** overwrite an existing `.env`)
5. Optional `--verify` — `zaumzeug doctor <name> --deploy` then `zaumzeug serve <name> --deploy --dry-run` (E5-S09c)
6. Print serve next steps

Shell wrappers (`target-install.sh` / `.ps1`) are polished in E5-S09b.

---

## Create `.env` on the target

1. If `.env.example` is present beside the project (or provided by ops), copy it to `.env` — **never overwrite** an existing `.env`.
2. Put provider API keys in `.env` only — never in YAML.
3. Confirm the ship folder has **no** `.env`: secrets are created on the target after copy.

## Serve on the target

From the **project root** that contains `deploy/<name>/` (parent of the bundle, not inside it):

```bash
zaumzeug doctor <name> --deploy
zaumzeug serve <name> --deploy
```

```powershell
# Windows (PowerShell) — same CLI
zaumzeug doctor <name> --deploy
zaumzeug serve <name> --deploy
```

Containers / systemd (no flag on every invocation):

```bash
export HARNESS_ROOT=deploy
zaumzeug serve <name>
```

```powershell
$env:HARNESS_ROOT = "deploy"
zaumzeug serve <name>
```

Same OpenAI REST surface as local serve (`POST /v1/chat/completions`, `GET /v1/models`). Validate without binding:

```bash
zaumzeug serve <name> --deploy --dry-run
```

## Platforms

| Role | Windows | macOS | Linux | CI-gated (v1) |
|---|---|---|---|---|
| **Developer workstation** (install, serve, compile, deploy CLI) | Primary | Primary | Primary | Yes — all three (E1-S07) |
| **Production serve** | Best-effort | Best-effort | **Primary** (VM, bare metal, Docker/K8s) | Linux only (`deploy` → `serve --deploy` smoke) |

The `deploy/<name>/` bundle is **OS-neutral** (Python 3.11+ sources, YAML/JSON, pinned artifacts — no OS-specific binaries). Linux is the supported ops target in v1. Windows/macOS production serve is supported **best-effort** and is **not CI-gated** in v1.

**Optional container path:** Generated Dockerfile in the bundle is Phase 4 ([E8-S05](../../docs/stories/epic-stories/62-story.md)). Until then, use `HARNESS_ROOT=deploy` in your own container image after `pip install zaumzeug`.

See also [PRD §14 — Cross-platform support](../../docs/prd.md#cross-platform-support) and [Architecture §10.6](../../docs/architecture/07-deploy-packaging.md#106-deploy-platform-targets).

## Updating production

| Situation | Action |
|---|---|
| **New harness revision** | On dev/CI: `zaumzeug deploy <name>` → copy new `deploy/<name>/` → re-run `target_install` → serve |
| **Do not** | `pip install -U …` ad hoc on the server to “refresh” the harness |
| **Runtime SDK bumps** | Come with the redeploy + `target_install` path (idempotent) |

## Git policy for deploy bundles

Default scaffolding ignores generated production output and compile artifacts (Architecture §10.4):

| Path | Default |
|---|---|
| `/deploy/` (repo root) | **Ignored** — local-only bundles |
| `usr-harnesses/*/artifacts/` | **Ignored** — harness-level generated artifacts |
| `artifacts/` (any depth) | **Ignored** — covers agent `agents/<name>/artifacts/` trees |
| `.env` | **Ignored** — never commit secrets |

**Audited releases:** Teams that want a release tag to pin an exact shippable tree may **force-add** a single bundle and commit it:

```bash
zaumzeug deploy <name>
git add -f deploy/<name>/
git commit -m "Release deploy/<name> for tag vX.Y.Z"
git tag vX.Y.Z
```

Remove or restore the ignore later with `git rm -r --cached deploy/<name>/` if you return to local-only bundles. Prefer CI artifact upload (below) when you need an audited binary without permanent git history.

**CI:** Pipelines may run `zaumzeug deploy <name>` and upload `deploy/<name>/` as a workflow artifact instead of (or in addition to) committing it — for example GitHub Actions `actions/upload-artifact` with `path: deploy/<name>/`.
